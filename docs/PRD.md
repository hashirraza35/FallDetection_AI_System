# Product Requirements Document

## FallDetection.AI

**Status:** Current product baseline  
**Version:** 1.0  
**Date:** 2026-10-03

## 1. Purpose

FallDetection.AI is a real-time fall detection and alerting application for monitoring a person in view of a camera attached to the machine running the Python application. It combines pose landmarks, temporal classification, motion checks, a browser dashboard, local incident history, and optional Telegram notifications.

This document captures the existing product behavior and defines the requirements for maintaining that behavior. It does not authorize changes to the trained model, detection thresholds, or inference architecture.

## 2. Problem Statement

A person monitoring a room may not continuously observe the camera feed. The application provides an automated indication of a possible fall, makes the monitoring state visible in a dashboard, records incidents, and can send a notification so someone can check on the person.

The system is an assistive alerting tool. It is not a substitute for supervision, emergency services, or medical diagnosis.

## 3. Goals

- Run the existing fall detection workflow against a locally attached camera.
- Provide an understandable browser dashboard for starting/stopping monitoring and viewing current state.
- Show recent incident records, confidence, severity, and Telegram delivery status.
- Preserve incident history locally across application restarts on the same persistent filesystem.
- Keep Telegram credentials out of source code and browser assets.
- Preserve the existing model and detection behavior while preparing the application for deployment.

## 4. Non-Goals

- Access a visitor's browser camera or transmit camera input from a remote examiner.
- Provide cloud-hosted video inference, WebRTC, or WebSocket camera transport.
- Provide medical diagnosis, guarantees of fall detection, or emergency response dispatch.
- Replace or retrain the current Random Forest model.
- Change fall thresholds, alert latch/recovery behavior, or Telegram alert logic as part of deployment preparation.
- Provide durable cloud storage for incidents or media in the current version.

## 5. Users and Use Cases

### Primary user: Local operator

The operator starts the Flask application on a computer with a camera, opens the dashboard, starts monitoring, observes system status, and stops monitoring when finished.

### Secondary user: Maintainer or examiner

The maintainer installs the documented Python environment, configures optional Telegram credentials, runs the application, inspects the model and alert history behavior, and understands the camera and hosting limitations.

## 6. User Stories

- As an operator, I can see whether the application and camera monitoring are active.
- As an operator, I can start and stop the inference process from the dashboard.
- As an operator, I can view processed live frames while monitoring is active.
- As an operator, I can see a fall alert and its severity/confidence when one is generated.
- As an operator, I can review recent incidents and whether Telegram delivery succeeded.
- As a maintainer, I can run the project from a clean Python 3.12 environment using the documented commands.
- As a maintainer, I can run without Telegram credentials and still use local detection and alert-history recording.

## 7. Functional Requirements

### 7.1 Application and monitoring lifecycle

- The Flask application shall serve the dashboard and expose the existing API routes.
- The dashboard shall start inference through `POST /api/start` and stop it through `POST /api/stop`.
- The application shall report current monitoring and alert state through `GET /api/status`.
- Inference shall use the existing OpenCV camera source on the host running Python.
- The dashboard shall show processed frames from `GET /video_feed` while monitoring is active.
- The application shall not start camera inference merely because the dashboard is opened.

### 7.2 Fall detection

- Inference shall continue using the existing MediaPipe Pose configuration and 33 pose landmarks.
- Inference shall use the existing 30-frame temporal input and the trained Random Forest model at `models/fall_detection_model.pkl`.
- Existing motion checks, thresholds, fall latch, and recovery behavior shall remain unchanged unless separately reviewed and approved.
- The application shall display the current ready, monitoring, or fall-detected state.

### 7.3 Incidents and notifications

- Each generated fall incident shall retain the existing incident fields, including ID, event, timestamp, severity, confidence, and Telegram status.
- Incidents shall continue to be stored in `outputs/alert_history.json` on the local filesystem.
- Each monitoring session shall use a unique MP4 filename so later sessions do not overwrite earlier recordings.
- Each incident generated by the existing fall latch shall get its own MP4 clip with buffered frames before and after detection; clip generation shall not change detection or alert decisions.
- Stopping monitoring through `POST /api/stop` shall request graceful inference shutdown so video writers can finalize their files before the process exits.
- `GET /api/alerts` shall return the current history with newest incidents first.
- Telegram delivery shall remain optional and use `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` from the environment or local `.env` file.
- Missing or failed Telegram delivery shall not prevent the local incident record from being saved.
- The dashboard shall present the latest alert, alert count, severity, confidence, and delivery status from the existing API data.

### 7.4 Dashboard and API

- The browser dashboard shall be served from the existing `DASHBOARD/` directory.
- Dashboard API requests shall use same-origin relative URLs.
- The existing routes shall remain available:

| Method | Route | Requirement |
| --- | --- | --- |
| GET | `/` | Serve the dashboard |
| POST | `/api/start` | Start local inference |
| POST | `/api/stop` | Stop local inference |
| GET | `/api/status` | Return system and monitoring status |
| GET | `/api/alerts` | Return persisted alert history |
| GET | `/video_feed` | Stream processed camera frames |

## 8. Data and Configuration

- **Runtime model:** `models/fall_detection_model.pkl`; required by live inference.
- **Training/evaluation features:** `data/urfd_extracted_features.csv`; not required for live inference.
- **Incident history:** `outputs/alert_history.json`; local runtime data.
- **Generated media:** live frame, unique session videos, and per-incident fall clips under `outputs/`; local runtime data.
- **Telegram configuration:** `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`; secrets must not be committed or exposed to frontend code.
- **Optional raw dataset path:** `UR_DATASET_DIR`; used only by feature extraction, defaulting to `data/ur_dataset`.
- **Runtime version:** Python 3.12.13 is the version verified with the current model and MediaPipe environment.

## 9. Quality and Security Requirements

- Project paths shall be derived from the project location rather than a developer-specific absolute path.
- Flask shall be importable by a WSGI server and honor the deployment-provided `PORT`.
- Production hosting shall use a production WSGI server and HTTPS.
- `.env`, virtual environments, caches, training features, and generated outputs shall be excluded from Git.
- The required model shall not be accidentally ignored.
- The application shall not print or return Telegram credential values.
- A pickle model shall only be loaded from a trusted source.
- UI/API confidence shall be described as a model score, not assumed to be a calibrated probability.

## 10. Acceptance Criteria

- A clean Python 3.12 environment can install dependencies from `requirements.txt`.
- `python app.py` serves the dashboard and honors `PORT` when set.
- The dashboard and read-only status/history endpoints return successfully.
- The required API routes remain registered and the dashboard continues using them.
- The current model deserializes and MediaPipe Pose initializes in the supported local environment.
- Starting and stopping monitoring remains controlled by the dashboard; these actions are validated on a machine with an available camera.
- Alert history remains readable and writable locally; Telegram notifications remain optional.
- No change in this preparation work modifies the model, thresholds, temporal sequence length, or fall/recovery logic.
- Documentation accurately states that cloud hosting alone does not provide access to a remote browser camera.

## 11. Constraints and Known Risks

- `cv2.VideoCapture(0)` opens a camera attached to the machine running the inference process. A cloud server cannot access a visitor's physical webcam through this architecture.
- The inference module imports Windows-only `winsound`; inference startup is not currently compatible with Linux hosts such as Render.
- Hosted filesystems may be ephemeral, so local alert history and media are not durable across instance replacement or redeployment.
- Computer-vision predictions can have false positives and false negatives. The model score is not established as a calibrated probability.
- Telegram delivery depends on valid credentials and network access.
- The application is not a certified medical device and must not be represented as one.

## 12. Future Work (Out of Scope for Current Baseline)

- A separately designed browser-camera workflow for remote examiner testing.
- Cross-platform audio alerts and inference startup.
- Durable hosted incident storage.
- Additional validation data and model calibration.
- Operational monitoring, retention policies, and deployment-specific access controls.

These items require separate design and approval; they are not claimed as implemented.
